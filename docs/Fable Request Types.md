# Fable Request Types

Based on the Fable training content and knowledge-base guidance, Fable requests fall into two broad categories:

- **Moderated requests**: live sessions with a tester on Zoom
- **Unmoderated requests**: testers complete tasks independently

## Request types

### 1. User Interview

A **User Interview** is a live, one-hour session with a person who uses assistive technology. During the meeting, you can ask questions, observe how they use websites or applications, and explore their experiences, challenges, and preferences. This request type is best when you want to understand why users behave a certain way or need exploratory feedback. Unlike unmoderated requests, you can ask follow-up questions and adjust the conversation in real time. Fable can also provide an Accessible Usability Scale (AUS) score if requested.

**Best for:** Research, discovery, accessibility education, and understanding user needs.

### 2. Prototype Review

A **Prototype Review** is a live session where a tester evaluates an interactive prototype, such as one created in Figma, InVision, or another design tool. Because the product does not need to be fully built, teams can gather accessibility feedback very early in the design process. Unlike a User Interview, the focus is on evaluating a proposed design rather than discussing broader experiences.

**Best for:** Early design validation and identifying accessibility issues before development begins.

### 3. QA Session

A **QA Session** is a live consultation with an experienced assistive technology user who evaluates your product and works through issues with you in real time. The emphasis is on problem-solving rather than discovery. Compared with a User Interview, the tester acts more like an accessibility expert, providing suggestions and recommendations while reviewing the product.

**Best for:** Accessibility troubleshooting, validating fixes, and getting expert guidance.

### 4. Self-Guided Task

A **Self-Guided Task** is an unmoderated test completed by a single tester. The tester records their screen and voice while independently attempting a task and describing their experience. You receive a video, transcript, and Accessible Usability Scale (AUS) score. The goal is to understand the overall usability and accessibility of a specific workflow from one person's perspective. Unlike Compatibility Tests, you get rich qualitative feedback and can see exactly what the tester experienced.

**Best for:** Understanding user experience, observing behaviour, and obtaining usability insights.

### 5. Compatibility Test

A **Compatibility Test** is an unmoderated request completed by five testers using different combinations of browsers, devices, and assistive technologies. Testers follow a clearly defined set of steps and provide structured written feedback. Unlike Self-Guided Tasks, there is no video recording. Instead, the focus is on identifying compatibility issues and measuring whether a task can be completed across multiple technology configurations.

**Best for:** Verifying accessibility across multiple assistive technologies and identifying cross-platform issues.

### 6. Page Audit

A **Page Audit** is an unmoderated review of a single web page against WCAG accessibility requirements. Multiple testers assess the page and Fable produces a structured report showing WCAG outcomes, identified issues, and where those issues occur on the page. Unlike Self-Guided Tasks and Compatibility Tests, the focus is not on completing a workflow but on evaluating the accessibility compliance of a page itself.

**Best for:** Accessibility compliance reviews, WCAG assessments, and identifying page-level accessibility defects.

### 7. Platform Surveys

Although not one of the main testing request types listed in Fable's request-type documentation, **Surveys** are generally used to gather structured opinions, ratings, or responses from testers without requiring a live session or detailed task completion. Surveys are quicker to run than interviews and are useful when you need quantitative feedback from a larger group of participants. The focus is on collecting responses rather than observing actual product usage.

**Best for:** Gathering opinions, measuring satisfaction, validating assumptions, and collecting quick feedback at scale.

## Quick comparison

| Request Type | Live? | Number of Testers | Main Output | Best Use |
|---|---:|---:|---|---|
| User Interview | Yes | 1 | Discussion, recording, transcript | Research and discovery |
| Prototype Review | Yes | 1 | Design feedback | Early design testing |
| QA Session | Yes | 1 | Expert recommendations | Troubleshooting accessibility issues |
| Self-Guided Task | No | 1 | Video, transcript, AUS score | Understanding user experience |
| Compatibility Test | No | 5 | Structured feedback and completion results | Cross-technology testing |
| Page Audit | No | Up to 7 | WCAG-based accessibility report | Compliance checking |
| Survey | No | Multiple | Responses and ratings | Gathering opinions and metrics |

## Easy way to remember them

- Want to ask questions? → **User Interview**
- Testing a design that isn't built yet? → **Prototype Review**
- Need expert accessibility advice? → **QA Session**
- Want to watch one user complete a task? → **Self-Guided Task**
- Want five testers to verify a workflow works across technologies? → **Compatibility Test**
- Want WCAG compliance findings on a page? → **Page Audit**
- Need quick feedback from many people? → **Survey**
